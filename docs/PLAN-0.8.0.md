# План реализации 0.8.0 — изоляция диалогов, запросов и проектов

Статус: **реализован в 0.8.0** (шаги 1–7; миграция проверена на эмуляторе на файле 1,7 МБ и на повреждённом файле диалога). Основа — раздел 0.8.0 в [ROADMAP.md](ROADMAP.md) и состояние кода на 0.7.8.

## Цель

Данные разных проектов и диалогов нельзя «слить в кучу»: ни по названию, ни через общий файл, ни через
общую рабочую папку. Повреждение одного диалога не должно задевать остальные, а обновление приложения
не должно терять историю.

## Что есть сейчас (проверено по коду 0.7.8)

| Область | Состояние | Риск |
|---------|-----------|------|
| Проекты | `files/workspaces/<UUID>`, метаданные в `state/projects.json` (`ProjectRepository`); имя на путь не влияет | одинаковые названия неразличимы в списках |
| Диалоги | один файл `state/chats.json` со **всеми** диалогами и сообщениями (`ChatRepository`); каждая запись переписывает файл целиком | рост файла, потеря всех диалогов при повреждении |
| Чтение файлов состояния | `JsonFileStore.read()` при ошибке разбора **молча возвращает пустое значение**, следующая запись затирает файл | тихая потеря данных |
| Диалог без проекта | `ChatSession.projectId` может быть `null`; при запуске `adoptOrphanSessions` приписывает такие диалоги выбранному проекту (`NeuroCodeApplication`) | запросы «без проекта» попадают в чужую папку |
| Вложения | `.neurocode/attachments` проекта, ссылка по относительному пути | копия диалога делила бы файлы с оригиналом |
| Копирование диалога | есть только копирование текста в буфер, дубликата диалога нет | — |

## Объём работ (по порядку выполнения)

### Шаг 1. Безопасное чтение состояния (основа для остального)

- `JsonFileStore.read()` различает «файла нет» и «файл повреждён»: повреждённый переименовывается в
  `<имя>.corrupt-<время>` и **не затирается**; в интерфейсе — уведомление «Файл … повреждён, копия сохранена»;
- запись остаётся атомарной (`.tmp` + переименование), добавляется `fsync` перед переименованием;
- тесты: пустой файл, обрезанный JSON, чужие поля, «файла нет», повреждённый файл не перезаписывается.

### Шаг 2. Различимые названия (интерфейс)

- чистая функция `ShortId.of(uuid)` (первые 4–6 символов) и `NameCollisions.find(names)`;
- короткий идентификатор показывается серым рядом с названием в шторке, выборе проекта и списке диалогов
  только когда названия совпадают (иначе лишний шум);
- создание проекта и импорт: если имя уже занято — предупреждение и кнопки «Создать отдельный» / «Другое имя»;
- тесты: одинаковые, отличающиеся регистром и пробелами названия; стабильность короткого идентификатора.

### Шаг 3. Диалог — один файл

Формат:

```text
files/state/chats/index.json        # [{id, title, projectId, createdAt, updatedAt, messageCount, model?}]
files/state/chats/<UUID>.json       # ChatSession целиком (сообщения, переопределение модели)
```

- новый слой `ChatStore` (чтение/запись одного диалога, индекс, удаление); `ChatRepository` сохраняет
  публичный интерфейс (`sessions`, `create`, `append`, `setModel`, `delete`, …), чтобы `ChatViewModel` не менялся;
- запись при `append` пишет только файл этого диалога и индекс; индекс пересобирается из файлов, если он
  потерян или не совпадает;
- повреждённый файл диалога карантинится (шаг 1), остальные загружаются; в списке такой диалог помечается;
- загрузка: на первом этапе читаются все файлы сразу; ленивая подгрузка сообщений — только если замеры
  покажут необходимость (порог: старт дольше 300 мс на 500 диалогах);
- тесты: запись одного диалога не трогает другие файлы, потеря индекса, повреждение одного файла,
  удаление, одновременные записи (mutex на диалог).

### Шаг 4. Миграция `chats.json` → файлы

Алгоритм (идемпотентный, с откатом):

1. если `chats/index.json` уже есть — ничего не делаем;
2. читаем `chats.json`; при ошибке разбора — карантин и **остановка миграции** (данные не теряются);
3. копируем `chats.json` в `chats.json.bak-0.8.0` (один раз, не перезаписывая);
4. пишем `chats/<UUID>.json` для каждого диалога, затем индекс;
5. проверяем: число файлов и сумма сообщений совпадают; только после этого `chats.json` переименовывается
   в `chats.json.migrated`;
6. при любом сбое — файлы нового формата удаляются, приложение продолжает работать на `chats.json`.

Тесты: пустой список, 1 и 500 диалогов, диалог без проекта, повторный запуск, сбой на середине.

### Шаг 5. Запросы без проекта — своя песочница

- у диалога без проекта создаётся скрытая рабочая папка `files/workspaces/<UUID диалога>` (флаг в метаданных,
  не показывается в списке проектов); инструменты агента, терминал и вложения работают в ней;
- `adoptOrphanSessions` удаляется: диалог больше не приписывается чужому проекту; уже приписанные при
  миграции 0.7.1 остаются как есть;
- удаление диалога удаляет и его песочницу; удаление проекта не затрагивает песочницы диалогов;
- тесты: два диалога без проекта не видят файлов друг друга; файл из песочницы не виден проекту;
  `PathGuard` не пропускает выход за корень песочницы.

### Шаг 6. Дублирование диалога

- действие «Дублировать» в меню диалога: новый UUID, новые UUID сообщений, копия переопределения модели;
- вложения копируются в новые файлы в `.neurocode/attachments` (имена с новыми идентификаторами), пути в
  сообщениях обновляются — общих файлов у оригинала и копии нет;
- тесты: удаление копии не удаляет вложения оригинала и наоборот.

### Шаг 7. Сквозные проверки изоляции

Сценарные unit-тесты (чистая JVM, без Android, на временной папке):

- два проекта и два диалога с одинаковыми названиями: перенос файлов между ними невозможен, удаление одного
  не затрагивает другой;
- переключение проекта показывает только его диалоги (фильтр по `projectId` из индекса);
- обновление с `chats.json` 0.7.8 сохраняет все сообщения, подписи моделей и вложения.

Проверка на эмуляторе: подложить `chats.json` с большим числом диалогов (как при проверке 0.7.8),
запустить, убедиться в миграции и в отсутствии зависаний; повторить с повреждённым файлом.

## Что не входит в 0.8.0

- доступ модели к файловой системе Android (`fs_*`, «корни доступа») — версии 0.8.1 и 0.8.2;
- ленивая подгрузка сообщений, поиск по диалогам и сжатие контекста — 0.8.3.

## Критерии готовности

- [ ] все тесты шагов 1–7 проходят, `detekt` без новых замечаний;
- [ ] миграция проверена на файле 0.7.8 с ≥ 100 диалогами и на повреждённом файле (эмулятор);
- [ ] ни один путь не записывает в `chats.json` после успешной миграции;
- [ ] повреждение одного файла диалога не мешает открыть остальные;
- [ ] документы (`ARCHITECTURE.md` — раздел «Хранилище», `README.md`, `ROADMAP.md`, `release_notes.txt`) обновлены.

## Риски

| Риск | Что делаем |
|------|------------|
| Потеря истории при миграции | резервная копия до записи, проверка количества, откат при сбое, миграция запускается один раз |
| Тихая перезапись повреждённого файла | шаг 1 выполняется первым и покрывает все файлы состояния, а не только диалоги |
| Рост числа файлов | индекс + карантин; ленивая загрузка при замерах выше порога |
| Гонки записи | один `Mutex` на диалог и один на индекс; запись через временный файл |
| Регрессия интерфейса | `ChatRepository` сохраняет публичный интерфейс; `ChatViewModel` и экраны не меняются |

## Порядок

Шаги выполняются по номерам 1 → 7 и выпускаются одной версией 0.8.0: шаги 1–4 — основа (безопасное
чтение, новый формат, миграция), без них шаги 5–7 не начинаются. После выпуска проверка на устройстве
обязательна до начала 0.8.1.
